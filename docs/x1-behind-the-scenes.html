The map

Two lanes. One lit box at a time.

Online — judges one change

A task is specified, an executor edits code, and the gate independently decides PASS, FAIL or NEEDS_HUMAN. This lane runs on every change.

Offline — grades the judge

A hidden answer key checks whether the gate’s verdict was right. It exists only for measurement. In production there is no oracle — which is why it is measured first.

How to read this deck

The strip above stays on screen. The dark box is where we are at each step. The dashed box — the Evidence Diversity Mapper — is designed but not built; it will never light up. That is honest, not an omission.

0:00–1:00 · Anchor the two lanes. Online = the product (the guardrail on every change). Offline = the clinical trial (known-answer tasks that measure the guardrail). Point at the dashed mapper box and say out loud that it is not built — credibility comes from the dashed box.

Step 1 · the task

A two-line ask with hidden depth.

$ cat demo/tasks/X1_v2.md

make Unidecode required, remove text-unidecode.
Constraints: do not modify test.py · use the project venv
· reinstall after changing setup.py.

Why this task probes blindspots

  • The two backends agree on almost every input — the visible 82 tests stay green either way
  • They disagree on a few: ₹500 → "500" vs "rs500" — and a slug is a URL
  • The task spans code + packaging + config — easy to complete selectively

02
Step 2 · baseline

Green before, or nothing after means anything.

$ python3 demo.py reset
82 passed in 0.04s
reset: release-gate-demo-base

What now exists on disk

  • workbench/python-slugify/ — clean clone at commit 42e5e792
  • workbench/task-venv/ — isolated interpreter
  • zero modified files — git status is empty

The rule

If the baseline is red, a later FAIL could mean “the AI broke it” or “it was already broken” — and no one can tell which. Green-before is the precondition for every verdict.

demo/python-slugify/demo.py · workbench/

0:00–1:00 · Baseline discipline. 12 of 25 well-known open-source repos failed this rule from a clean clone when the corpus was measured. Never assume green; verify it at the pinned commit in the gate’s own environment.

Step 3 · the candidate

A candidate is just a diff nobody accepted yet.

$ python3 demo.py control pass   # scripted candidate
M README.md · M setup.py · M slugify/slugify.py · M tox.ini

- install_requires = ['text-unidecode>=1.3']
+ install_requires = ['Unidecode>=1.1.1']
- try: import unidecode
- except ImportError: import text_unidecode …
+ import unidecode

Two ways this box gets filled

  • Live runs: GitHub Copilot CLI edits the code — 5 recorded runs, mean 88 s, ~12 AIC each
  • This demo: a pre-scripted patch (a lab control) — deterministic, so the gate’s behaviour is repeatable on stage

Either way the gate sees the same thing: 4 changed files.

demo/python-slugify/controls/pass.patch · demo/runs/RUNLOG.md

0:00–1:15 · Define “candidate” and “control”. Candidate = proposed change awaiting judgment. Control = pre-scripted candidate with a known correct verdict, used to prove the instrument reads correctly — same sense as a lab control. The AI is interchangeable here by design: the gate must not care who wrote the diff.

Step 4 · the gate begins

First move: trust nothing, rebuild everything.

$ release-gate run --repo . --base release-gate-demo-base
capturing worktree… reconstructing base + candidate
in an isolated workspace…

Identity is pinned before judging

  • base commit 42e5e792a247
  • patch sha256 7e8bd4232c58… — fingerprint of exactly what is judged
  • policy sha256 4c52b4fbbb8a… — fingerprint of the rules used

Why rebuild?

The executor’s workspace can lie — ambient packages and cached state make incomplete work look healthy. In live run-01, Copilot reported “82 passed” from the wrong interpreter; the gate’s clean rebuild found the tests could not even run.

.release-gate/runs/<run-id>/result.json → base_commit, patch_sha256, config_sha256

0:00–1:15 · Independence, made physical. The gate reconstructs both base and candidate from git in its own workspace. Nothing the executor claims is carried over. The three hashes make the verdict attributable: this exact diff, judged under this exact policy, from this exact base.

0:00–1:00 · Paths are intent. Before any test runs, the gate reads intent from the file list. Step 6 · evidence checks

Three checks, three kinds of evidence.

checkmodeseveritywhat it provesthis run
tests-and-coveragedifferentialblocking runs the suite on base and candidate; asserts candidate-minus-baseline failures ≤ 0 — works even on messy repos PASS
task-consistencycandidateblocking asserts remaining == 0 leftover text_unidecode references — the “half-finished task” detector PASS
typescandidateadvisory mypy — advisory: a failure here escalates to a human, it cannot FAIL the run alone PASS

Evidence, not opinion

Each check runs a real command, saves its report, and parses it into typed assertions — e.g. junit /failures · candidate-minus-baseline · lte 0 · passed: true.

A blindspot became a check

In live runs 4–5 the AI skipped tox.ini and nothing could see it. task-consistency is that exact gap, promoted into gate policy.

result.json → checks[].assertions · effective-config.json → checks

0:00–1:30 · Read one assertion aloud. The differential mode is the answer to “our repo is a mess”: the question is never “is everything green?” but “did this change make it worse?”. And task-consistency is the improvement loop working: a real observed AI failure (runs 4–5, tox.ini left stale) became a deterministic check. That is how a gate learns.

07
Step 7 · the verdict

One rule turns evidence into a decision.

Precedence — NEEDS_HUMAN > FAIL > PASS

  • any check ERROR / SKIPPED → NEEDS_HUMAN — unverified work is never a pass or a fail
  • any blocking check fails → FAIL
  • any advisory check fails → NEEDS_HUMAN
  • otherwise → PASS · reason codes cleared
VERDICT: PASS
reason_codes: []            exit 0
RESULT: .release-gate/runs/
  20260827T143722Z-58368f55bad1/result.json

The line most gates get wrong

A check that could not run is not evidence against the candidate — and not evidence for it. It outranks FAIL on purpose: claiming knowledge you don’t have is how a gate becomes theatre.

src/release_gate/policy.py → aggregate_verdict() · result.json → verdict

0:00–1:15 · Adverse vs missing, first pass. FAIL means evidence says the candidate is wrong. NEEDS_HUMAN means the gate cannot verify — tool missing, timeout, check skipped, judge edited. Exit codes: 0 PASS, 1 FAIL, 2 NEEDS_HUMAN. This distinction returns on slide 12 with receipts.

08
Step 8 · what’s on disk

The verdict comes with receipts.

.release-gate/runs/20260827T143722Z-58368f55bad1/
├ result.json            verdict · checks · scope · hashes
├ trace.json             12 events · what ran, when, exit codes
├ manifest.json          every artifact + its sha256
├ candidate.patch        the exact diff that was judged
├ effective-config.json  the policy that applied
└ observability/         rolling-rate snapshot

Why it matters

  • A verdict you can’t reconstruct is an opinion. Every claim here traces to a file.
  • Tamper-evident: the manifest hashes each artifact — edit one and the hashes disagree.
  • Weeks later, “why did this pass?” has an answer that doesn’t depend on memory.
manifest.json → artifacts[].sha256 · trace.json → control_finished events

0:00–1:15 · The audit story. result.json is the decision record; trace.json is the how (commands, exit codes, durations, truncation flags); manifest.json binds it together with hashes. Tamper-evident, not immutable — an honest distinction the tool itself makes.

09
Step 9 · offline lane

Was the gate right? Only the answer key knows.

$ python3 demo.py grade --result …/result.json
16 passed in 0.06s
truth: correct
classification: good_pass

The hidden oracle

  • 16 asserts the gate never sees — the divergent inputs: ₹500→rs500 · ♥ love→hearts-love …
  • expected values were observed by running both backends first — never guessed
  • good_pass = gate said PASS and the change was truly correct — “good” grades the gate, not the code

Production has no oracle

That is the whole point of the offline lane: measure the gate on known answers first, then trust its verdicts where no answer key exists. Production can reveal a bad pass eventually — it can never reveal a wrongly blocked good change.

demo/python-slugify/oracle/test_x1_oracle.py · demo.py grade

0:00–1:30 · The asymmetry argument. A false release eventually surfaces in production. A false block never does — the change didn’t ship, nothing happened, no trace. Only a bench with hidden answers sees both error directions. This is the sharpest idea in the whole design; give it its 30 seconds.

Executor’s workspace hides missing dependencies. Seen live in run-01. Countered by the clean rebuild.

Blindspot B · selective completion

Code lands, config lags (tox.ini, runs 4–5). Countered by task-consistency.

11
Step 11 · the distinction that matters

“Evidence of failure” ≠ “failure to get evidence.”

FAIL — adverse evidence

A check ran and found the candidate wrong. Receipt: control fail → PATH_FORBIDDEN · forbidden: test.py. The evidence argues against release.

NEEDS_HUMAN — insufficient evidence

Checks never ran. Receipt: control needs-human → checks SKIPPED (POLICY_FILE_CHANGED). The gate refuses to judge on evidence it doesn’t have.

The live-run proof · run-01 → run-01b

Copilot: “82 passed.” The gate’s clean rebuild: pytest exit 2 — tests could not run (missing dependency). Verdict NEEDS_HUMAN, not FAIL. One human pip install later, re-gated: PASS, oracle 15/15, good_pass. The task never “failed” — the gate briefly couldn’t verify it.

demo/runs/RUNLOG.md · run-01 tests.log (pytest exit 2)

0:00–1:30 · K’s core teaching point. Never translate gate ≠ PASS into “the engineering task failed”. Four different states hide behind a red light: the candidate is wrong; evidence is missing; a check itself broke; a human is required. The gate names which one — read the reason codes, not the color.

12
Step 12 · the numbers, honestly

What we can measure today — and what we can’t yet.

Verdict rates · built

Every run feeds a dashboard: rolling 10 and 100-run windows of release / fail / human-review rates, with config-change markers.

Cost · measured live

5 Copilot runs on X1: mean 88 s, ~12 AIC each. 5/5 correct — but 0 fails in 4 runs still allows a true failure rate up to 49% (Wilson). Five runs size the bill; they don’t qualify a pipeline.

Not built yet

No token-budget loop (MORE_EVIDENCE_REQUIRED), no cost-vs-review saturation curve, and the diversity mapper never lit up. Naming the gaps is part of the evidence.

The one-sentence takeaway

evidence → sufficiency → policy → verdict. The gate is an assurance system, not another test runner — it turns “the agent says it’s done” into a decision you can audit.
