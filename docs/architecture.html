K's richness point, in one look: the slugify gate would score high on “number of tests” (82!) yet spans only four families; the rate-limiter gauntlet has fewer tests and twice the span. Diversity of families is what makes evidence hard to fool — many tests of one kind can share one blindspot. Widening the span is where Graphify-style signals (AST / control-flow / data-flow) come in: they tell a planner where behaviour exists that no evidence family currently touches. The hook for that is already in the skill (read-only Graphify advisory); the enrichment loop that would consume it is diagram 2's red loop — not built.

4 · How controls get built

A control is a candidate whose correct verdict you already know, kept as a frozen patch. It is how you prove the gate reads correctly — the same idea as a lab control sample.

The recipe (any repo)

  • Pin a baseline commit where the suite is green
  • Freeze a change as a patch file with a known verdict
  • State the expected verdict and reason codes next to it
  • Run gate → compare → any mismatch is a gate bug

Where big repos get them free

  • Your git history: a real bug-fix commit reversed = a known-bad candidate; the fix itself = known-good
  • Reverted PRs: merged-then-reverted changes are labelled false-releases, ready made
  • Tamper controls: any good change + one edit to a test, CI file, or gate policy
  • No-op control: an empty change must PASS — if it doesn't, the gate is broken, not the code

The rule that keeps gates honest

Every check ships with at least one control that makes it fire. A check that has never been seen to fail is indistinguishable from a check that scans nothing — the scaffolding's B7 checker passed for weeks while inspecting zero files.
