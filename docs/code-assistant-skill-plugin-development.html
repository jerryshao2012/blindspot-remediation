A practical introduction to skill & plugin development

From promptto product.

Skills turn repeatable engineering judgment into a workflow. Plugins make that workflow installable, versioned, and supportable across teams.

SKILL.mdwhen + what + boundaries
deterministic corescripts, tools, services
plugin / archiveinstall, upgrade, rollback

0:00–0:30 · Open with the problem. Ask: “How many useful prompts or review checklists are currently trapped in one person’s chat history?” Pause for hands. That is the gap this session addresses.

0:30–1:20 · Establish the vocabulary. A prompt is a one-off instruction. A skill is a reusable workflow contract the assistant can discover and follow. A plugin is the installable distribution boundary around one or more skills and related capabilities.

1:20–2:15 · Explain the pipeline. SKILL.md says when to run and how to work. Deterministic code handles facts or policy that must be reproducible. Packaging adds installation, upgrades, compatibility, and rollback.

2:15–3:00 · State the thesis. This is not “more prompt engineering.” We are turning team judgment into an artifact we can test, version, qualify, and support. Release Gate 0.6.0 is the real example for the rest of the talk.

Transition: “Before we build anything, we need to choose the smallest extension that actually fits the job.”

0:00–1:15 · Walk the decision questions left to right. Instructions apply by default. A skill runs a repeatable procedure on demand. An agent brings specialist context and a constrained toolset. MCP or hooks connect live systems or enforce lifecycle rules. A plugin distributes a versioned bundle.

1:15–2:15 · Define a skill concretely. Its entry point is SKILL.md. The description is routing metadata; the body specifies inputs, ordered steps, decisions, outputs, verification, and safe stops. Put detailed policy in references/, repeatable mechanics in scripts/, and reusable files in assets/.

2:15–3:00 · Define a plugin concretely. It is a host-specific installable bundle that can include skills, agents, hooks, MCP configuration, and assets. Manifests and lifecycle commands vary by host; the core workflow should not.

3:00–3:45 · Give the selection rule. Start with one standalone skill while the workflow is changing. Add a plugin only when distribution, versioning, multiple related components, or external integration is a real requirement—not a prediction.

3:45–4:35 · Explain the development loop. Define positive, adjacent, and negative requests. Author the portable boundary. Add thin host adapters. Qualify discovery, routing, behavior, security, and the packaged artifact.

4:35–5:00 · Audience check. Ask for one current team workflow. Quickly classify it using the five questions. Reinforce: “portable core, host-specific shell.”

Transition: “Release Gate shows what this separation looks like in production code.”

0:00–1:15 · Read the left side as a contract. The portable skill is intentionally small: two-field frontmatter, an explicit trigger, required inputs, ordered calls, exact output semantics, and stop rules. The description says “use only when explicitly invoked,” so discovery is not authorization.

1:15–2:00 · Explain progressive disclosure. SKILL.md stays readable. Exact compatibility lives in JSON, longer policy guidance lives in initialization.md, and the Codex UI metadata lives in agents/openai.yaml. Load details only when the workflow reaches them.

2:00–2:40 · Point to the bridge. The skill does not reproduce the release algorithm in prose. It makes exact CLI calls. That keeps the model responsible for orchestration and the executable responsible for enforcement.

2:40–4:35 · Walk the deterministic core. First, require the exact compatibility string release-gate 0.6.0. Then reconstruct trusted base and candidate workspaces and run bounded argument vectors without a shell. Preserve the engine’s PASS, FAIL, or NEEDS_HUMAN verdict. Finally, write atomic, tamper-evident evidence.

4:35–5:25 · Clarify the safety boundary. The skill calls the gate once. It never reinterprets, retries, merges, deploys, or upgrades NEEDS_HUMAN into PASS. Reporting may follow, but it remains non-gating.

5:25–6:00 · Name the common mistake. Do not ask the model to “inspect the diff and decide if release is safe” when the decision must be reproducible. Let the model guide; let code decide. Evidence is tamper-evident, not immutable, and PASS covers only configured policy.

Transition: “Now let’s build and invoke this exact skill, one development state at a time.”

0:00–2:00 · Author. Point to the two-field frontmatter: name and description. Say: “The description is a router, so it must include the positive trigger and the negative boundary.” Then show the body rule: never infer a subcommand and never treat skill discovery as authorization.

2:00–4:00 · Validate. Advance once. python tests/validate_skill.py checks frontmatter, reachable references, schemas, exact commands, safety invariants, and version synchronization. Explain that routing tests need positive, paraphrase, negative, and adjacent prompts in fresh sessions; avoid prose snapshot tests that fail on harmless wording.

4:00–6:00 · Package. Advance again. python scripts/build_skill_archives.py --output-dir dist creates four archives from one canonical source: Copilot, Codex, Claude Code, and Antigravity. Sorted members, fixed timestamps, normalized line endings, and SHA-256 make the deliverables reproducible.

6:00–8:45 · Invoke. Advance to the last state. First call release-gate --version and require exactly release-gate 0.6.0. Then validate configuration and run once with release-gate run --repo . --base <ref>. Read .release-gate/runs/<id>/result.json before giving advice.

8:45–9:30 · Explain the three outcomes. PASS means configured policy passed; it is not merge authorization. FAIL means a deterministic policy check failed. NEEDS_HUMAN is a first-class result for unresolved judgment—not an error to retry away.

9:30–10:00 · Land the lesson. The skill never softens, reinterprets, retries, merges, or deploys. Ask: “Which part of your current assistant workflow should become deterministic code?”

Transition: “A working source tree is not a release. The installed artifact still has to prove itself.”

0:00–1:30 · Read the first row. Discovery proves the host lists the installed component from the expected source. Routing proves the description accepts positive and paraphrased requests while rejecting negative and adjacent ones. Behavior proves required structure, tools, permissions, failures, and side effects.

1:30–2:40 · Read the second row. Adversarial tests keep repository text as untrusted data. Artifact tests inspect paths, file types, exact versions, schemas, checksums, and byte-for-byte reproducibility. Fresh-install qualification runs against the archive or marketplace candidate—not the convenient source checkout.

2:40–3:45 · Make it a supply-chain story. Pin dependencies, generate checksums, install the exact candidate, run smoke tests in a clean environment, record the supported host matrix, and retain a rollback path. A green source test is necessary but insufficient.

3:45–5:15 · Deliver the three takeaways. First, start with a skill and package only when distribution demands it. Second, keep enforcement deterministic: instructions orchestrate, code validates and decides. Third, release only the exact artifacts you tested.

5:15–6:00 · Close with action. Ask each team to nominate one repeated workflow, define its positive and negative requests, and prototype it as a standalone skill before the next engineering review. Final line: “Portable workflow. Deterministic core. Host-qualified delivery.”
