Create a NEW repository from the existing L1 engineering automation repository.

Do not modify the original repository.

The new repository must be a smaller, laptop-runnable version whose scope ends at the release gate. It must also include a local API connector to an LLM so that a developer can run the complete truncated pipeline from a laptop.

Read the existing repository first and reuse its relevant code, contracts, comments, tests, design rationale, and evaluation logic. Preserve substantive code verbatim wherever possible. Only modify code where necessary to remove downstream dependencies or make the system runnable locally.

SCOPE

Keep only the engineering path through:

TaskRequest
ChangeExecutionService
CandidateArtifact
ReleaseGateService
GateDecision

GateDecision must support:

PASS
FAIL
HUMAN_REVIEW_REQUIRED

GateDecision is the terminal online domain result.

The repository must NOT:

deploy code to production;
observe released code in production;
collect post-release operational metrics; calculate process outcomes; calculate business KPIs; implement production feedback loops; automatically modify prompts or policies from production feedback; implement production rollback or deployment.

It is acceptable to return, print, persist, or publish GateDecision. Nothing after that belongs to this repository.

LOCAL LAPTOP EXECUTION

The new repository must run on a normal developer laptop.

Do not require Azure, Jira, Service Bus, containers, or enterprise infrastructure for the default local path.

Provide a simple local execution mode using the local filesystem and Python subprocess execution in a temporary isolated working directory.

The local mode should be clearly documented as a development/POC execution environment, not production-grade security isolation.

A developer should be able to:

1. create a Python virtual environment;
2. install the package;
3. set LLM API environment variables;
4. run one sample X1 task;
5. inspect the generated candidate;
6. run the release gate;
7. receive PASS, FAIL, or HUMAN_REVIEW_REQUIRED; 8. run a small offline evaluation campaign.

LLM API CONNECTOR

Create one provider-neutral ModelClientPort and one practical HTTP/API implementation suitable for laptop use.

Prefer an OpenAI-compatible API interface because many model gateways expose that shape.

Configuration should use environment variables similar to:

L1_LLM_BASE_URL
L1_LLM_API_KEY
L1_LLM_MODEL

Optionally support:

L1_LLM_TIMEOUT_SECONDS
L1_LLM_MAX_RETRIES

Do not hard-code secrets.

Do not commit API keys.

Provide a .env.example or equivalent example configuration containing placeholders only.

The application code must not directly call an LLM SDK from ChangeExecutionService or ReleaseGateService. Those components receive ModelClientPort through dependency injection.

The model connector should capture:

model identifier;
request purpose;
input token usage when reported;
output token usage when reported;
latency;
retry count;
provider errors.

If the selected API does not report token counts, represent that explicitly rather than inventing values.

The connector should support structured JSON responses where the calling component requires structured output.

Validate structured responses before using them.

LOCAL MODEL FAILURE SEMANTICS

A model API timeout, authentication failure, rate limit, malformed response, or network failure must not silently become GateOutcome.FAIL or GateOutcome.PASS.

Use typed infrastructure/model exceptions.

If required gate evidence cannot be generated because the LLM service is unavailable, the release-gate workflow should normally end in HUMAN_REVIEW_REQUIRED or an explicit execution failure according to the existing gate semantics.

Never manufacture evidence.

LOCAL EXECUTION SAFETY

Because this runs on a laptop, make the limitations clear.

Generated code is potentially unsafe.

For the POC:

use a temporary working directory;
set execution timeouts;
restrict commands to configured/approved commands; do not pass unrelated environment secrets into subprocesses; do not give generated code access to the LLM API key unless absolutely required; avoid network-dependent tests by default; clean up temporary workspaces when safe to do so.

Document that this is development isolation, not a production sandbox.
