Release Gate · 0.6.0 Engineering demo

Independent release evidence

Proof before release.

A policy-driven gate between AI-generated code and the production repository.

RG

0:00–0:45 · Introduce the core problem. Open with the premise: AI code assistants generate code quickly, but how do we independently verify that candidate changes meet strict release criteria before touching production?

0:45–1:30 · Introduce Release Gate 0.6.0. Explain that Release Gate is an independent, policy-driven verification gate between AI-generated code and the production repository, providing deterministic proof rather than self-attestation.

Transition: “Let’s look at why standard green tests alone are not enough for release decisions.”

The blindspot

Green tests are not a release decision.

0:00–0:40 · Context Blindspot. An assistant operates in its own dirty workspace with cached state and ambient packages. What works on the dev machine often fails in clean environments.

0:40–1:20 · Coverage Blindspot. Real tasks span packaging, tox environments, docs, and configurations. AI agents frequently miss non-code files or peripheral configs.

1:20–2:00 · Authority Boundary. A candidate change must never grade itself. If an agent weakens the test suite or modifies gate policy, it must be caught by an independent trust boundary.

0:00–0:50 · Clean Reconstruction. Every run starts from a clean base and applies the candidate patch in isolation. We rebuild both base and candidate workspaces from scratch.

0:00–1:00 · Sliding Window Contract. Explain the sliding window: a hit at t=0 must remain active through t=60 and only expire when age strictly exceeds 60 seconds (t > 60).

1:00–1:50 · The Boundary Defect. Using >= drops the request at the exact boundary, violating the rate limiting contract.

1:50–2:30 · Mutation Analysis. Inverted operators (<=) corrupt the state machine completely. Subtleties like this require mutation-backed test depth.
