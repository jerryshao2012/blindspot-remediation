0:00–0:45 · Framing the Challenge. As AI code assistants and autonomous agents enter enterprise workflows, their speed generates a new bottleneck: release confidence. An agent declaring "all tests passed" is not evidence for release.

0:45–1:30 · The Release Gate Objective. Release Gate sits between candidate generation and the release pipeline as an independent, deterministic evaluator that proves repository consistency, behavioral correctness, and human-bounded governance.

Transition: “Let’s look at the foundational blindspot that necessitates this architecture.”

The blindspot

Green tests are not a release decision.

01 / CONTEXT

The assistant sees its dirty workspace. Cached bytecode and ambient host packages make incomplete work look healthy. When tested from a clean clone, it breaks.

02 / COVERAGE

Real tasks span more than happy-path code. Agents easily miss packaging configs (setup.py), test matrices (tox.ini), documentation, or peripheral dependencies.

03 / AUTHORITY

The candidate cannot grade itself. A candidate change must never have the authority to edit its own judging criteria, weaken test assertions, or bypass security rules.

Core Architectural Invariant

Release Gate reconstructs all verification from a reviewed git base in isolated sandboxes — independent of the agent’s subjective confidence.

0:00–0:45 · Context Blindspot. Dev machines and assistant environments carry state. In real runs, Copilot reported "82 passed" on python-slugify from the wrong host interpreter; clean rebuild showed it couldn't run.

0:45–1:30 · Coverage Blindspot. Incomplete migrations: code imports updated, but tox.ini and setup.py left stale. Standard CI runs only happy paths.

1:30–2:00 · Authority Boundary. If an agent modifies a test file or gate policy, the gate must not accept it blindly; it must escalate directly to human review.

Transition: “Here is the 6-stage proof pipeline that enforces this invariant.”

The architecture

One candidate. Six stages of independent proof.

STAGE 01

Candidate Intake

Fingerprints the candidate patch SHA-256 and base commit SHA before touching disk.

STAGE 02

Clean Rebuild

Reconstructs base and candidate in pristine, isolated virtual environments.

STAGE 03

Reviewed Policy

Enforces wildmatch path scoping: allowed, forbidden (test.py), and review-required.

STAGE 04

Evidence Ledger

Differential tests, task consistency checks, and 10-layer quality gauntlets.

STAGE 05

Three-Way Verdict

Deterministic evaluation: PASS, FAIL, or NEEDS_HUMAN with reason codes.

STAGE 06

Human Review

Production ends with evidence review and a human release decision.

0:00–1:00 · Stages 1 through 3. Every run begins with cryptographic pinning of git base and patch digest. Both environments are reconstructed from scratch, and file scope is validated against policy.

1:00–2:00 · Stages 4 through 6. Real command executions produce parsed assertion evidence. A deterministic precedence rule produces the verdict, then production ends with evidence review and a human release decision. Oracle grading belongs to offline known-answer qualification.

Transition: “When a defect is detected in Demo 02, how does Release Gate safely automate repair?”

Demo 02 · rate-limiter · Bounded Repair
TRACK 2: BOUNDED REPAIR GOVERNANCE & HUMAN GATE

Automation can repair — inside explicit authority.

Human Authorization Gate

When C0 fails (FAIL), the gate halts immediately at awaiting_approval. The agent cannot proceed without explicit human signoff.

Strict Attempt Budget

Human approval permits exactly 2 paths and caps repair at 2 attempts. If C1 and C2 fail, the session aborts to prevent runaway agent loops.

Disposable Sandbox

C1 and C2 are evaluated in isolated temporary worktrees. The primary source repository remains byte-for-byte at C0 until final approval.

state machine: C0 FAIL -> approval -> C1 FAIL -> C2 PASS -> final approval -> applied
verify-repair: C0 FAIL -> C1 FAIL -> C2 PASS -> applied (total 4m12s)
Detailed Walkthrough: docs/rate-limiter-behind-the-scenes.html

0:00–1:00 · The Governance Challenge (Demo 02). Autonomous coding agents can easily enter infinite loops, generate compounding errors, or silently edit tests. Bounded repair solves this with explicit human bounds.

1:00–2:30 · Cryptographic Transactional Apply. The passing C2 patch is applied to the source worktree only once, after a final human approval bound to the patch SHA-256 digest, session ID, and timestamp.

Transition: “Let’s look at how verdicts are determined and audited.”

The verdict rule

“Evidence of failure” ≠ “failure to get evidence.”

FAIL — Adverse Evidence

A configured check ran and proved the candidate incorrect. The evidence argues decisively against release.

NEEDS_HUMAN — Insufficient Evidence

Checks never completed — tool missing, timeout, policy modified, or scope violated. The gate refuses to judge without evidence.

Precedence Rule & Tamper-Evident Receipts

NEEDS_HUMAN > FAIL > PASS. Every run records result.json, trace.json, and manifest.json (SHA-256 of every artifact) for complete auditability.

0:00–1:00 · Precedence Rule. NEEDS_HUMAN outranks FAIL because claiming knowledge you don't have is how a gate becomes security theatre. If a tool crashes or policy is touched, it must escalate.

1:00–2:00 · Receipts on Disk. All decisions produce tamper-evident manifest hashes. Six months later, you can prove exactly why a commit passed or failed.
